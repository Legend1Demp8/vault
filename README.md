# HashiCorp Vault — 3-Node Raft Cluster with HAProxy (Docker)

Отказоустойчивый трехнодовый кластер **HashiCorp Vault** в Docker Compose на базе встроенного хранилища **Integrated Storage (Raft)** с балансировщиком нагрузки **HAProxy** и автоматическим выпуском самоподписанных TLS-сертификатов через сервис `nip.io`.

## Особенности архитектуры

* **Кластер из 3 нод (`vault-node1`, `vault-node2`, `vault-node3`).** Обеспечивает кворум и отказоустойчивость: при выходе из строя одной ноды кластер автоматически выбирает нового лидера и продолжает работу без потери данных.
* **Единая точка входа и балансировка (`vault-haproxy`).** Контейнер HAProxy:
  * Принимает клиентский HTTPS-трафик на стандартном порту **443** по общему домену `https://vault.<HOST_IP>.nip.io` (API и Web UI).
  * Отслеживает состояние нод через эндпоинт `GET /v1/sys/health` и направляет весь трафик **исключительно на активного лидера** (код `200`), автоматически отсекая резервные (`429 Standby`) и запечатанные (`503 Sealed`) ноды.
  * Предоставляет веб-панель мониторинга состояния кластера на порту **8404** (`https://vault.<HOST_IP>.nip.io:8404/stats`).
* **Схема инициализации 3 из 5 (Shamir's Secret Sharing).** Главный ключ шифрования при инициализации делится на 5 частей, для разблокировки (`unseal`) требуются любые 3 ключа.
* **Автоматический PKI и конфигурирование (`vault-cert-gen`).** Вспомогательный контейнер на базе Alpine при запуске:
  * Генерирует корневой центр сертификации (`certs/ca/ca.crt`).
  * Выпускает индивидуальные TLS-сертификаты сроком на **365 дней** для каждой ноды (`vault{1..3}.<HOST_IP>.nip.io`) и объединенный сертификат (`vault.pem`) для единой точки входа HAProxy (`vault.<HOST_IP>.nip.io`).
  * Автоматически перевыпускает сертификаты, если до истечения их срока действия осталось менее **30 дней**.
  * Генерирует конфигурационные файлы `node{1..3}/config/vault.hcl` и `haproxy/haproxy.cfg` из шаблонов `.tpl`.
* **Изоляция ключей и сквозное шифрование (End-to-End TLS).** Трафик шифруется на всех участках (клиент → HAProxy → ноды Vault). Каждый сервис монтирует в режиме `read-only` только свою директорию с сертификатами (`certs/vault1..3` или `certs/haproxy`).

## Структура проекта

```text
.
├── .env                  # Файл переменных окружения (HOST_IP, версии образов)
├── .gitignore            # Исключения Git (сертификаты, базы Raft, .env, сгенерированные конфиги)
├── docker-compose.yml    # Описание сервисов, портов и внутренней сети с DNS-алиасами
├── generate-certs.sh     # Скрипт генерации TLS-сертификатов и конфигов из шаблонов
├── haproxy.cfg.tpl       # Шаблон конфигурации балансировщика HAProxy
├── vault.hcl.tpl         # Шаблон конфигурации ноды HashiCorp Vault
├── certs/                # Сгенерированные CA и TLS-сертификаты (не хранится в Git)
│   ├── ca/               # Корневой сертификат и ключ CA
│   ├── haproxy/          # Объединенный сертификат vault.pem и ca.crt для HAProxy
│   └── vault{1..3}/      # Индивидуальные сертификаты и ключи для нод Vault
├── haproxy/              # Сгенерированный haproxy.cfg (не хранится в Git)
└── node{1..3}/
    └── config/           # Сгенерированный vault.hcl для конкретной ноды
```

## Сетевые порты и точки доступа

| Сервис / Назначение | Адрес доступа | Порт на хосте | Описание |
| :--- | :--- | :---: | :--- |
| **Vault UI / API (HAProxy)** | `https://vault.<HOST_IP>.nip.io/ui/` | `443` | Единая точка входа, всегда ведет на активного лидера |
| **HAProxy Stats** | `https://vault.<HOST_IP>.nip.io:8404/stats` | `8404` | Веб-панель мониторинга состояния нод и переключений |
| **Vault Node 1 (прямой)** | `https://vault1.<HOST_IP>.nip.io:18201` | `18201` | Прямой доступ к первой ноде  |
| **Vault Node 2 (прямой)** | `https://vault2.<HOST_IP>.nip.io:18202` | `18202` | Прямой доступ ко второй ноде |
| **Vault Node 3 (прямой)** | `https://vault3.<HOST_IP>.nip.io:18203` | `18203` | Прямой доступ к третьей ноде |

## Настройка перед запуском

### 1. Подготовка переменных окружения (`.env`)

Клонируйте репозиторий

Перейдите в папку с проектом

Откройте `.env` и укажите **внутренний IP-адрес** вашего сервера в переменной `HOST_IP`:

```env
VAULT_VERSION=2.2.2
ALPINE_VERSION=3.24.4
HAPROXY_VERSION=3.0-alpine
HOST_IP=192.168.1.50
```

* `VAULT_VERSION` — закрепленная версия образа `hashicorp/vault`.
* `ALPINE_VERSION` — закрепленная версия образа `alpine` для init-контейнера.
* `HAPROXY_VERSION` — закрепленная версия образа `haproxy`.
* `HOST_IP` — единственный IP-адрес хоста без пробелов, на базе которого формируются домены `nip.io`.

## Запуск и сборка кластера

### 1. Старт контейнеров

```bash
docker compose up -d
```

Контейнер `vault-cert-gen` создаст сертификаты, сгенерирует файлы `vault.hcl` и завершится со статусом `Exited (0)`, после чего запустятся все три ноды Vault.

### 2. Инициализация первой ноды

Выполните инициализацию на `vault-node1`:

```bash
docker exec -it vault-node1 vault operator init
```

**Что делает эта команда:**
* `docker exec -it vault-node1` — подключается к работающему контейнеру `vault-node1` в интерактивном режиме.
* `vault operator init` — запускает процесс инициализации хранилища внутри контейнера.

**Результат выполнения:**
После успешного запуска в консоль будут выведены:
1. **Unseal Keys (Ключи распечатывания)** — по умолчанию 5 ключей (для распечатывания потребуются любые 3 из них).
2. **Initial Root Token (Корневой токен)** — главный токен с полными правами администратора.

> ⚠️ **Важно:** Обязательно сохраните сгенерированные ключи и токен в надежном защищенном месте (например, в менеджере паролей). Без этих ключей вы не сможете разблокировать Vault после перезапуска контейнера, а повторный запуск `init` выдаст ошибку.

### 3. Проверка статуса всех нод кластера

После инициализации первой ноды необходимо проверить текущее состояние всех узлов кластера. В выводе команды `vault status` мы убедимся, что ноды видят инициализацию, а также узнаем, сколько ключей требуется для их распечатывания.

Выполните проверку поочередно для каждой ноды (на примере кластера из трех узлов — `vault-node1`, `vault-node2`, `vault-node3`):

```bash
docker exec -it vault-node1 vault status
docker exec -it vault-node2 vault status
docker exec -it vault-node3 vault status
```

**На что обращать внимание в выводе:**
* **`Initialized: true`** — подтверждает, что хранилище успешно инициализировано. *(Примечание: на резервных нодах `vault-node2` и `vault-node3` это значение может оставаться `false` до тех пор, пока вы не распечатаете первую ноду и они не синхронизируются по протоколу Raft — это нормальное поведение).*
* **`Sealed: true`** — означает, что нода находится в запечатанном (заблокированном) состоянии и пока не может отдавать секреты.
* **`Threshold: 3` и `Total Shares: 5`** — показывает параметры ключа Шамира: всего создано 5 ключей, для разблокировки ноды требуется ввести любые 3.
* **`Unseal Progress: 0/3`** — счетчик введенных ключей распечатывания. До начала разблокировки он равен `0/3`.
* **`Storage Type: raft` и `HA Enabled: true`** — подтверждает, что используется встроенное кластерное хранилище Raft и включен режим высокой доступности (High Availability).

### 4. Распечатывание (Unseal) всех нод кластера

После запуска и инициализации все ноды находятся в запечатанном состоянии (`Sealed: true`). Чтобы перевести кластер в рабочий режим, необходимо разблокировать каждую ноду.

Процедура выполняется поочередно для каждого узла. Начните с `vault-node1` (которая станет лидером кластера), а затем повторите процесс для остальных нод:

```bash
# 1. Распечатываем первую ноду (будущего лидера)
docker exec -it vault-node1 vault operator unseal

# 2. Распечатываем остальные ноды (после ввода 3-го ключа они автоматически подключатся к лидеру через retry_join)
docker exec -it vault-node2 vault operator unseal
docker exec -it vault-node3 vault operator unseal
```

**Как проходит процесс ввода ключей:**
1. Выполните команду `vault operator unseal` для первой ноды. Консоль запросит ввод ключа (`Unseal Key (will be hidden):`).
2. Вставьте первый из сохраненных ключей и нажмите `Enter` (вводимые символы не отображаются на экране в целях безопасности). В выводе статус `Unseal Progress` изменится на `1/3`.
3. Повторите команду еще **2 раза**, каждый раз подставляя **другой** уникальный ключ из 5 полученных при инициализации.
4. После ввода третьего ключа (`3/3`) нода разблокируется. Повторите те же 3 шага для `vault-node2` и `vault-node3`.

> 💡 **Примечание:** Для распечатывания всех нод используются **одни и те же 3 ключа**. Отдельных наборов ключей для каждой ноды не существует.

#### Проверка результата распечатывания

После завершения процедуры на всех узлах повторите проверку статуса из **пункта 3**, чтобы убедиться, что кластер успешно собрался:

```bash
docker exec -it vault-node1 vault status
docker exec -it vault-node2 vault status
docker exec -it vault-node3 vault status
```

**На что обращать внимание в обновленном выводе:**
* **`Sealed: false`** — подтверждает, что нода успешно распечатана и готова к работе (на всех узлах значение должно измениться с `true` на `false`).
* **`Initialized: true`** — теперь отображается как `true` абсолютно на всех нодах, включая реплики.
* **`HA Mode: active` / `standby`** — в выводе появятся новые строки статуса высокой доступности. Одна из нод (обычно `vault-node1`) получит статус `active` (лидер), а остальные — `standby` (резервные узлы, готовые перехватить управление).
* **`Raft Committed Index` и `Raft Applied Index`** — появляются у распечатанных нод и подтверждают, что репликация данных внутри кластера работает корректно.

### 5. Авторизация и проверка состояния кластера

После распечатывания всех нод необходимо войти в систему с правами администратора и убедиться, что все узлы успешно объединились в единый кластер Raft.

#### Шаг 1. Авторизация в Vault

Выполните команду входа на ноде-лидере (`vault-node1`):

```bash
docker exec -it vault-node1 vault login
```

**Как проходит авторизация:**
1. Консоль запросит токен: `Token (will be hidden):`.
2. Вставьте **`Initial Root Token`**, который вы сохранили на этапе инициализации (пункт 2), и нажмите `Enter` (символы при вводе скрыты).
3. При успешном входе появится сводка с параметрами токена (такими как `token_policies: ["root"]` и `token_duration: infinity`).

> 💡 **Примечание:** После выполнения `vault login` токен сохраняется внутри контейнера `vault-node1` (в файле `/root/.vault-token` или в домашней директории пользователя), поэтому последующие команды на этой ноде не будут запрашивать его повторно.

#### Шаг 2. Проверка участников кластера Raft

Теперь запросите список всех узлов, входящих в кластер:

```bash
docker exec -it vault-node1 vault operator raft list-peers
```

**Пример успешного вывода:**
```text
Node     Address              State       Voter
----     -------              -----       -----
node1    vault-node1:8201     leader      true
node2    vault-node2:8201     follower    true
node3    vault-node3:8201     follower    true
```

**На что обращать внимание в выводе:**
* **`Node`** — идентификаторы (`node_id`) всех узлов, заданные в конфигурации Vault. В списке должны присутствовать все три ноды (`node1`, `node2`, `node3`).
* **`Address`** — внутренние адреса и кластерные порты (по умолчанию `8201`), по которым ноды обмениваются данными и реплицируют хранилище.
* **`State`** — текущая роль каждого узла в кластере:
  * **`leader`** — главный узел (ровно один на весь кластер), который принимает все запросы на запись и управляет репликацией данных.
  * **`follower`** — резервные реплики, которые синхронизируют данные с лидера и готовы провести выборы нового лидера в случае его сбоя.
* **`Voter: true`** — подтверждает, что узел является полноправным участником кворума и имеет право голоса при выборах лидера.

> ⚠️ **Рекомендация по безопасности:** `Initial Root Token` обладает неограниченными правами в системе. В промышленной эксплуатации (Production) его рекомендуется использовать только для первичной настройки (создания методов аутентификации, политик и административных пользователей), после чего отозвать командой `vault token revoke -self`.

### 6. **Проверка отказоустойчивости кластера через HAProxy:**

Убедитесь, что балансировщик корректно отслеживает состояние нод и автоматически переключает трафик при сбоях.

* **Откройте панель статистики HAProxy:**
Перейдите в браузере по адресу https://vault.<HOST_IP>.nip.io:8404/stats. Изначально активной (основной) нодой является `vault-node1`, а ноды `vault-node2` и `vault-node3` находятся в резерве.

* **Имитируйте отказ основной ноды:**
```bash
docker stop vault-node1
```

* **Проверьте автоматическое переключение:**
Снова обновите страницу статистики. Нода `vault-node1` перейдет в статус `DOWN`, а весь клиентский трафик автоматически переключится на единственную оставшуюся в строю ноду **`vault-node3`**.

* **Верните ноду в строй:**
После завершения проверки запустите остановленный контейнер обратно:
```bash
docker start vault-node1
```

* **Распечатайте ноду:**
После запуска контейнера разблокируйте ноду используя сохраненные Unseal Key 
```
docker exec -it vault-node1 vault operator unseal
```

## Эксплуатация и обслуживание

### Перезапуск контейнеров или сервера
При рестарте контейнеров ноды автоматически переходят в состояние `Sealed`. Для возврата в работу достаточно заново выполнить шаги `vault operator unseal` (ввести 3 ключа) на каждой ноде.

### Продление TLS-сертификатов
Скрипт `generate-certs.sh` проверяет срок действия сертификатов и перевыпускает их только если осталось меньше **30 дней**. Чтобы проверить и обновить сертификаты без перезагрузки нод и повторного ввода `unseal`-ключей:

```bash
docker compose restart cert-gen
docker kill -s SIGHUP vault-node1 vault-node2 vault-node3
```
